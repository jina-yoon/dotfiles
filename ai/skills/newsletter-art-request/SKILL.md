# Newsletter art requests

Jina files art requests as GitHub issues in `PostHog/marketing`. There are two kinds, and she usually files both for the same newsletter on the same day:

1. **Hero image** — the header image for the newsletter. One image, plus a few words of text set into it.
2. **Polish pass** — the designers clean up infographics that already exist in rough form, usually SVGs generated by Claude.

Your job is to write the issue body in her voice, get her approval, file it, and (for polish passes) get the SVGs into Figma.

## The one thing that matters most: keep it short

Her past requests are short. A hero request is often four sentences plus a bulleted TL;DR. A polish pass is often a numbered list of images with almost no prose.

The rule she cares about, in her words: **whatever can be understood already from looking at the graphic does not need to be described in words.** If you have embedded an image of a chart, do not narrate the chart. The designer can see it. Writing "the Y axis shows how much code is written by agents" under a picture whose Y axis is labelled "How much of the code is written by agents?" wastes their time and reads as condescending.

The exception is **intent that is invisible in the artifact**. In one past request the shaded region on a chart deliberately feathered out at the edges because there is no exact point where a codebase becomes a software factory. A designer tidying that up would have squared off the edges and destroyed the argument. That is worth a sentence, because looking at the image does not tell you it was on purpose. So the test for every sentence you write is: *could the designer get this by looking at the picture?* If yes, cut it. If it is about why something is the way it is, or what it must not lose, keep it.

Before you show her a draft, reread it and delete the sentences that fail that test. Drafts are almost always too long on the first pass, and the second pass is usually still too long. A polish pass for three graphics should be around a hundred words. A hero request should be around two hundred.

Two specific things that bloat these requests and must not appear: a block of art direction or recommendations addressed to the designer, and any sentence explaining which of your suggested concepts is best. She lists options and lets them choose.

## Her voice

Read `references/examples.md` for four real past requests, verbatim. Match them rather than inventing a style. The short version:

- Plain and direct. "I'm writing a newsletter about X." Not "This request is for the creation of a hero image asset."
- Casual sign-offs and asides are normal: "Same as usual for newsletter :)", "Open to suggestions!", "sorry this is a bit late". Do not manufacture these, but do not strip them out if she says something like that either.
- She hedges honestly when she is unsure: "Still deciding on the hero image text", "Not sure which of these need polish, feel free to skip if you think they're fine as-is!". Keep her uncertainty in. Fake confidence makes designers do the wrong work.
- Bullets for the TL;DR of an article, prose for everything else.
- **No em dashes.** She has complained about this in a real issue thread after Claude filed one for her. Use commas, parentheses, or a full stop.
- Do not add headings the template does not have. Do not add a summary of what you just wrote.

## Workflow

### 1. Ask which kind

Use AskUserQuestion: hero image, polish pass, or both. If she picks one, ask whether she wants the other too, since she almost always files them as a pair and they cross-reference each other.

### 2. Read the Google Doc first

Ask for the doc link if she has not given one, then read it with the Claude in Chrome browser tools (her Google login lives in her Chrome session, so `WebFetch` will not work on a docs.google.com link). Open it in a new tab and use `get_page_text`.

Reading the doc first is what makes this skill worth using. It means you can *propose* the TL;DR bullets, a hero image text drawn from the actual headline, and a list of the infographics in the doc, instead of making her type all of it out. Come to her with a draft, not a form.

While reading, note:

- The working headline and subtitle.
- The three-ish load-bearing arguments, for the TL;DR bullets on a hero request.
- Every image in the doc, for a polish pass. Note roughly where each one sits in the article and what it is called.

### 3. Ask for what the doc cannot tell you

In one message, ask only what is genuinely missing. Typically:

- **Deadline.** Write down exactly what she says. Do not add warnings about lead time and do not invent a default date.
- **Hero image text** (hero requests only). Propose one drawn from the headline and let her correct it. If she is not sure yet, say so in the issue and mark it a placeholder, which is what she has done before.
- **Imagery ideas** (hero requests only). Propose two or three concrete concepts based on the article, as a bulleted list, and let her pick or replace them. She often ranks them by preference and adds "very open to new ideas".
- **Anything to add.** Notes, constraints, references, whether she is OOO.

Skip anything you already know. Do not ask her to confirm build mode, it always is.

### 4. Write the issue

Follow `references/templates.md` for the exact body structure of each kind, and `references/examples.md` for tone.

Every request is build mode, so a hero request always carries this line, bolded, as its own paragraph:

> **This is for build mode, so it should have build mode styling and logos.**

**Build mode heroes are simple graphics, not Max the hedgehog.** This matters when you propose imagery. Her older requests are full of Max: Max as a wizard, Max in the style of a "for dummies" book, Max supervising a robot stamping PRs. Those predate build mode and are the wrong reference now. The build mode hero for the software factories issue was, in her words, "the image should probably just have a factory in it?" One clear object or idea, rendered simply, with a few words of text set into it.

So propose concepts as objects and situations rather than as scenes starring a character. If every idea you have written starts with "Max", you are drawing on the old newsletters, and you should go back to the article and ask what the piece is actually about instead.

Titles:

- `Art request - Hero image for <topic> newsletter`
- `Art request - Polish pass for <topic> newsletter`

### 5. For polish passes, find the existing SVGs and get them into Figma

**Go and find the real files. Do not regenerate them.**

If the graphics in the doc were made with Claude, the source SVGs already exist on Jina's machine, and finding them is most of the value of this skill. Rebuilding a graphic from a screenshot produces something that looks close and is not the same file, which means the designer polishes the wrong artifact and her revisions are silently lost. Falling back to "these were generated with Claude so I don't have a Figma link" when the file was sitting in Downloads all along is the single most annoying way this skill can fail.

Read `references/svg-discovery.md` for how to find them. The short version: they are in `~/Downloads`, named in snake_case after what they depict, usually with a matching `.png` of the same stem, and there are almost always several versions of the same graphic, so the newest one wins. Search before you ask, and ask before you guess.

Then read `references/figma.md` to place them on the "build mode graphics" page, so the issue can link to a real Figma section. Do this before filing, since the link goes in the body.

Only use the "I don't have a Figma link to provide" fallback when you have actually searched and come up empty, and say that you searched.

### 6. Show her the draft, then file

Show the full issue body (both, if it is a pair) and wait for approval. Do not file first and edit after.

On approval, file in `PostHog/marketing` with:

- label `artwork`
- assignees `lottiecoxon`, `dphawkins1617`, `heidiberton`

The template also adds it to the Art & Brand Planning board (`PostHog/65`). If your tools cannot set the project, file the issue anyway and tell her it needs adding to the board.

**Order matters for a pair.** File the hero first so you have its number, then file the polish pass referencing it, then edit the hero to add the trailing cross-link. Do not leave a `#TBD` in either body.

Give her the issue URLs when you are done. One line. She does not need a recap of what the issues say, she just approved them.
